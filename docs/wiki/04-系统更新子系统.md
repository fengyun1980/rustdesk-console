# 04 — 系统更新子系统（Updater）

## 4.1 概述

Updater 是一个 **完全独立于 NestJS API 的子系统**，负责后端 + 前端容器/二进制的有序更新、数据备份、故障回滚和恢复。它以 **独立进程** 运行，与 API 通过 **Unix Domain Socket** 通信，有自己的进程锁、状态存储、维护栅栏。

### 关键设计原则

| 原则 | 实现 |
|------|------|
| 独立进程模型 | updater 不加载 TypeORM、不导入任何 NestJS module；由 `--system-update-mode=` 在入口分派 |
| IPC 通信 | Unix Socket（默认 `/run/rustdesk-console-updater/control.sock`），API 侧是客户端 |
| 维护栅栏（Maintenance Fence） | 更新期间写 `maintenance.json`；API 的 middleware 读此文件返回 503 |
| 进程锁 | `acquireProcessLock()` 保证同一状态目录只跑一个 updater / worker |
| 故障恢复 | 每个阶段记录 intent，恢复模式可重放中断任务 |
| 部署适配器 | Compose 和 Linux 两种部署有各自的 Adapter（策略模式） |

## 4.3 进程模型

### 三种运行模式（`src/updater/entrypoint.ts`）

通过命令行参数 `--system-update-mode=<mode>` 切换：

```
┌─────────────────────────────────────────────────────────────┐
│  mode = 'updater'        （长时间运行的控制面）              │
│  ├── 监听 SYSTEM_UPDATE_SOCKET                              │
│  ├── 定期 reconcile()（每 10s）                            │
│  ├── 接收 API 端的 IPC 请求                                 │
│  └── 为每个 job 启动独立 worker 进程                        │
└─────────────────────────────────────────────────────────────┘
                              │ spawn
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  mode = 'worker' --job-id=<uuid>                           │
│  ├── 读取 job record                                        │
│  ├── acquire 执行锁（execution.lock）                       │
│  ├── run(jobId) → 阶段式执行流水线                          │
│  └── 完成/失败后释放锁                                        │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  mode = 'recover' --job-id=<uuid>                           │
│  ├── 验证 record 的恢复决策                                  │
│  ├── 更新状态为 'running'                                   │
│  └── 委托 deployment.startWorker(jobId) 交给 supervisor     │
└─────────────────────────────────────────────────────────────┘
```

### 入口分派（`src/main.ts`）

```ts
const mode = process.argv
  .find((v) => v.startsWith('--system-update-mode='))
  ?.split('=')[1];

if (mode) {
  // Dispatch before loading TypeORM; updater never opens business DB.
  const { updaterMain } = await import('./updater/entrypoint.js');
  await updaterMain(mode);
  return;
}
```

updater 进程 **刻意** 在 NestJS/TypeORM 加载前 return，避免污染内存。

## 4.4 IPC 协议

### Socket 端点

- API 侧（客户端）：`SystemUpdateService` 通过 `SYSTEM_UPDATE_SOCKET`（默认 `/run/rustdesk-console-updater/control.sock`）发送 JSON 请求。
- updater 侧（服务端）：`UpdateControl.listen()` 监听并分发到对应 handler。

### 请求/响应 JSON 协议

```json
// Request
{ "method": "capabilities", "params": {} }
{ "method": "plans",        "params": { "target": { "channel": "stable" } } }
{ "method": "jobs.create",  "params": { "planId": "uuid", "downtimeAcknowledged": true } }
{ "method": "jobs.current", "params": {} }
{ "method": "jobs.get",     "params": { "jobId": "uuid" } }

// Response
{ "success": true, "result": { ... } }
{ "success": false, "error": { "code": "BLOCKED", "message": "..." } }
```

### 支持的 IPC 方法

| Method | 作用 |
|--------|------|
| `health` | updater 存活 + 当前版本 |
| `capabilities` | 当前安装的可更新性、部署类型、数据库类型 |
| `plans` | 生成更新计划（目标版本、阻塞项、预计停机） |
| `jobs.create` | 创建并启动一次更新 job |
| `jobs.current` | 正在执行或最近一次 job |
| `jobs.get` | 查询指定 job |

## 4.5 核心类

### UpdateControl（控制面）

**文件**: [control.ts](file:///workspace/src/updater/control.ts)

- 维护 Unix Socket 监听（`listen(socketPath)`）
- 解析 IPC 请求 → 分派到 handler
- `jobs.create` → 幂等性检查 → 持久化 record → 调用 `deployment.startWorker(jobId)` 启动独立 worker 进程
- `reconcile()` 每 10s 轮询：发现 worker 崩溃则重启（不重新创建 record）
- 更新进程组权限（`chmod` socket 到 `SYSTEM_UPDATE_SOCKET_GID`）

### Planner（计划生成）

**文件**: [planner.ts](file:///workspace/src/updater/planner.ts)

- 查询 `OfficialCatalog` 可用版本
- 校验 release manifest：版本、SHA、签名、过期时间
- 做 **预检（preflight）**：
  - 部署状态是否一致（compose 服务都在）
  - 磁盘空间足够
  - 当前版本是否是可升级源
  - 是否有其他 job 正在执行（互斥）
- 返回 `{ blockers, operations, estimatedDowntime, target }`

### UpdateWorker（执行流水线）

**文件**: [worker.ts](file:///workspace/src/updater/worker.ts)

```
阶段式流水线（每个阶段有 intent 写入，可恢复）：

  prepare           ← 下载 artifact、解压到 staging
  maintenance       ← 写 maintenance fence、通知 API 进入只读
  backup            ← 调 BackupAdapter 备份数据库 + 业务文件
  switching         ← 调 DeploymentAdapter 切换镜像/二进制
  verifying         ← healthcheck（HTTP 200）、迁移完整性
  helper            ← 如有 helper 组件更新（db 客户端工具等）
  commit            ← 成功：移除 maintenance fence、finalize
  recovery          ← 失败入口：根据 decision 回滚 / 恢复数据
```

### UpdateStore（状态存储）

**文件**: [store.ts](file:///workspace/src/updater/store.ts)

- 以 JSON 文件持久化 job record 到 `stateDir`
- 每次阶段完成写入 `operations.<stage> = 'done'`
- `decision` 字段记录恢复决策（restore_data / rollback_only / manual）

## 4.6 部署适配器

工厂根据 `installation.deployment` 类型选择：

| 适配器 | 部署类型 | 关键方法 |
|--------|----------|----------|
| [ComposeDeployment](file:///workspace/src/updater/adapters/compose.ts) | `managed-compose`（Docker Compose 托管） | `pull`, `stop`, `override`（digest 锁定）, `up`, `verify`（healthcheck）, `startWorker`（启 worker 容器） |
| [LinuxDeployment](file:///workspace/src/updater/adapters/linux.ts) | `native-linux`（SEA 二进制 + systemd） | `prepare`, `stop`（systemctl stop）, `switch`（符号链接切换）, `start`（systemctl restart）, `verify` |

Compose 适配器有额外的 digest 锁定机制：每次更新在 `docker-compose.override.yml` 写入镜像 digest，防止自动拉取变更镜像。

## 4.7 备份适配器

**文件**: [backups/](file:///workspace/src/updater/backups/)

```ts
createBackupAdapter(installation.database)
// → MySQL  → MysqlBackupAdapter
// → SQLite → SqliteBackupAdapter
```

### SQLite

- 使用 `VACUUM INTO` 或 `.backup database.sqlite` 原子复制
- 同时备份业务文件（`DATA_DIR/` 下的 custom-client builds 等）
- `requireStopped()` 确保 API 进程已停止后再备份

### MySQL/MariaDB

- `mysqldump` 生成 logical dump（DDL + INSERT）
- 导入时先用空库创建结构，再导入数据，最后 `CHECK TABLE` + 行数校验
- 恢复前必须停掉 API，保证一致性

## 4.8 维护模式栅栏

**文件**: [maintenance.ts](file:///workspace/src/updater/maintenance.ts)

```
updater (worker)                     API NestJS
     │                                   │
     ├─ 写 maintenance.json              ├─ middleware 读此文件
     │  { status: 'active',              │  businessWritesAllowed()
     │    reason: 'SYSTEM_UPDATE',        │  → false → HTTP 503
     │    startedAt: ... }               │
     │                                   │
     │               API 返回 503        │
     │               /api/system-update  │  豁免！
     │               /health             │
     │                                   │
     ├─ 所有阶段完成                     ├─ 写成功后移除 fence
     └─ 删 maintenance.json              │
```

API 侧拦截逻辑在 `application.ts:39-57` 的 middleware：

```ts
if (
  !businessWritesAllowed() &&
  request.path !== '/api/system-update/health' &&
  !isSystemUpdateStatusRequest
) {
  response.status(503).setHeader('Retry-After', '5');
  response.json({ code: 'SYSTEM_MAINTENANCE', ... });
}
```

应用启动时 `waitForApplicationStart()` 会阻塞直到 fence 解除。

## 4.9 恢复流程

当 worker 在 **backup 后** 的阶段崩溃（说明新镜像/二进制已可能部分生效），恢复需要：

1. `mode = 'recover'` 启动，指定 `--job-id=<uuid>`。
2. 检查 `record.decision`：如果 restore_data = 'intent' 但未标记 done，说明数据恢复不确定，退出让管理员手动介入。
3. 否则把状态置回 `running`，交由 `deployment.startWorker(jobId)` 继续执行（或回滚）。
4. 工具脚本 `deployment/rustdesk-console-recover` 封装此流程。

## 4.12 设计要点总结

| 特性 | 实现 |
|------|------|
| 进程隔离 | updater 入口在 TypeORM/NestJS 加载前 return |
| 通信协议 | Unix Socket + JSON-RPC 风格 |
| 状态持久化 | 文件系统 JSON（UpdateStore），每个阶段有 intent |
| 并发控制 | 状态目录级进程锁（`control.lock` / `execution.lock`） |
| 维护围栏 | JSON 文件 + API middleware 拦截 |
| 部署抽象 | ComposeDeployment / LinuxDeployment 策略模式 |
| 备份抽象 | MysqlBackupAdapter / SqliteBackupAdapter |
| 恢复 | 阶段 intent + decision 字段驱动的恢复流水线 |
| 安全 | `requireStopped()` 写操作必须停进程、SHA 校验 manifest、digest 锁定 |
